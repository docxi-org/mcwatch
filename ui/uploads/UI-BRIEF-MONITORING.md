# Бриф на экран мониторинга

Один дополнительный экран. Здесь — **что** он показывает и как себя ведёт.
Внешний вид решает исполнитель.

Требование-первоисточник — `docs/TASK.md`, дополнительная часть 2:
«мониторить процесс работы сервиса в реальном времени (статусы воркеров,
количество обработанных записей и т.п.) и кнопку принудительного запуска».

---

## 1. Зачем экран

Сервис работает сам по себе: раз в час просыпается, идёт на Metacritic,
собирает игры, потом просит нейросеть написать резюме, потом считает векторы
для похожих. Всё это занимает минуты и происходит без участия человека.

Экран отвечает на четыре вопроса:

1. Сервис вообще жив и работает?
2. Чем он занят прямо сейчас?
3. Сколько сделал и сколько сломалось?
4. Можно ли запустить обработку прямо сейчас, не дожидаясь часа?

Аудитория — владелец сервиса, а не посетитель каталога. Экран служебный.

## 2. Три воркера

Работа поделена на три этапа, они идут строго по очереди:

| Воркер | Что делает | Сколько длится |
|---|---|---|
| `crawler` | Обходит Metacritic, забирает игры и отзывы | Минуты: к источнику не чаще одного запроса в секунду |
| `summarizer` | Просит нейросеть написать резюме по отзывам | Минуты |
| `embedder` | Считает векторы для подбора похожих игр | Секунды |

Один прогон всех трёх называется **циклом**. Цикл запускается раз в час
автоматически либо кнопкой.

Важно: **сбой одного этапа не отменяет следующие.** Если обход не удался,
резюме всё равно считаются — по играм, которые уже в базе. Поэтому «у crawler
ошибка» не означает «сервис сломан».

## 3. Что показывать

### 3.1 Состояние воркеров

По каждому из трёх:

- **состояние**: `idle` (простаивает), `running` (работает), `error`
  (последний прогон закончился ошибкой);
- **чем занят сейчас** — название игры или описание пачки; у простаивающего
  пусто;
- **обработано всего** и **ошибок всего** — счётчики накопительные, за всё
  время жизни сервиса, а не за последний цикл. Они переживают перезапуск;
- **когда работал в последний раз**;
- **последняя ошибка**, если была.

Воркер появляется в списке только после первого запуска. **На свежем сервисе
список пуст** — это нормальное состояние, а не сбой.

### 3.2 Состояние обхода

Отдельно от воркеров: на какой день собирает, в какой фазе (`landing` — первые
20 игр с главной, `browse` — очередная страница общего списка), номер следующей
страницы и сколько игр уже обработано сегодня.

### 3.3 Журнал событий

Лента: время, воркер, уровень (`info` / `warn` / `error`), сообщение и
необязательные подробности объектом. Свежие сверху. Хранится не больше
5000 записей, старые вытесняются.

### 3.4 Кнопка принудительного запуска

Запускает цикл немедленно. Три исхода, и все три надо показать по-разному:

| Ответ | Что произошло | Что показать |
|---|---|---|
| `202` | Цикл запущен | Кнопка становится недоступна, состояние переходит в «работает» |
| `409` | Цикл уже идёт | Сказать, что запуск уже идёт. Это не ошибка |
| `503` | Планировщик выключен настройкой | Объяснить, что запуск недоступен, кнопка неактивна |

Кнопка не ждёт окончания: ответ приходит сразу, цикл идёт минуты. Прогресс
виден по потоку событий, а не по ответу на нажатие.

## 4. Реальное время

Главное требование ТЗ. Данные приходят потоком **Server-Sent Events**.

Особенность, которую надо учесть при проектировании: **обход длится минуты, и
события журнала за это время редки**. Между «воркер начал работу» и «воркер
закончил» может пройти пять минут. Живость видна не по журналу, а по снимкам
состояния — они приходят на каждую обработанную игру: меняется «чем занят» и
растут счётчики.

То есть **экран не должен выглядеть замершим, пока идёт долгий обход**.
Смена текущего элемента и рост счётчиков — основной признак жизни.

## 5. Контракт API

### `GET /api/status`

Полный снимок. Годится и для первой отрисовки, и для обновления по требованию.

```jsonc
{
  "workers": [
    {
      "worker": "crawler",
      "state": "running",              // "idle" | "running" | "error"
      "currentItem": "Onimusha: Way of the Sword",  // null у простаивающего
      "processedTotal": 42,            // накопительно за всё время
      "failedTotal": 1,
      "lastRunAt": "2026-09-07T12:00:00.000Z",      // может быть null
      "lastError": null                             // текст последней ошибки
    }
  ],
  "crawl": {                           // может быть null: обхода ещё не было
    "date": "2026-09-07",              // календарная дата UTC
    "phase": "landing",                // "landing" | "browse"
    "nextPage": 1,
    "processedToday": 20
  },
  "cycleRunning": true,                // идёт ли цикл прямо сейчас
  "schedulerEnabled": true,            // включён ли планировщик вообще
  "events": [                          // последние 50, свежие первыми
    {
      "id": 128,
      "ts": "2026-09-07T12:03:11.000Z",
      "worker": "crawler",
      "level": "info",                 // "info" | "warn" | "error"
      "message": "заход начат",
      "data": { "date": "2026-09-07", "target": { "phase": "landing" } }
    }
  ],
  "serverTime": "2026-09-07T12:03:20.000Z"
}
```

`serverTime` полезен, чтобы считать «минуту назад» по часам сервера, а не
браузера.

### `GET /api/events` — поток SSE

Каждый кадр — строка `data:` с JSON вида `{ "event": "...", "data": ... }`.
Три вида кадров:

```jsonc
// 1. Снимок состояния. Приходит первым сразу после подключения,
//    затем на каждое изменение — то есть на каждую обработанную запись.
{ "event": "status", "data": { "workers": [ /* как в /api/status */ ],
                               "cycleRunning": true } }

// 2. Событие журнала. Редкие, но содержательные.
{ "event": "event", "data": { "id": 129, "ts": "...", "worker": "crawler",
                              "level": "warn", "message": "игра не собрана: xyz",
                              "data": { "error": "HTTP 500 на ..." } } }

// 3. Признак жизни. Приходит раз в 20 секунд, когда ничего не происходит.
//    Показывать не нужно — он только держит соединение.
{ "event": "ping", "data": "" }
```

Первый кадр — всегда снимок, так что отдельно дёргать `/api/status` перед
подпиской не требуется.

Соединение стоит переподключать при обрыве: сервис может перезапуститься.

### `POST /api/crawl/run`

Тела запроса нет.

| Код | Тело |
|---|---|
| 202 | `{"started": true}` |
| 409 | `{"error": "already_running"}` |
| 503 | `{"error": "scheduler_disabled", "message": "Планировщик выключен в настройках"}` |

## 6. Состояния, которые обязательно случатся

| Состояние | Что делать |
|---|---|
| **Свежий сервис**: воркеров нет, `crawl` — `null` | Сказать, что работы ещё не было, а не показывать пустую таблицу |
| **Долгая тишина**: цикл идёт, но событий журнала нет | Живость показывать по «чем занят» и счётчикам |
| **Поток оборвался** | Переподключиться; пока нет связи — сказать об этом честно |
| **`state: error` у одного воркера** | Не подавать как отказ всего сервиса: остальные этапы отработали |
| **`schedulerEnabled: false`** | Автоматических циклов нет; кнопка неактивна с пояснением |
| **Ошибок больше, чем успехов** | Счётчик ошибок должен быть заметен, но не кричать: часть игр у источника битая, это норма |

## 7. Чего не делать

- Не изобретать управление сверх кнопки запуска: остановки цикла, перезапуска
  воркеров, правки настроек в API нет;
- не показывать `data` события сырым JSON без возможности свернуть — там
  бывают длинные объекты;
- не смешивать этот экран со списком игр: это разные аудитории.

## 8. Что нужно прислать

Компоненты Vue 3 + TypeScript, встроенные в то же приложение, что и каталог,
отдельным маршрутом. Подписка на SSE с переподключением при обрыве. Данные —
только из трёх маршрутов выше.
